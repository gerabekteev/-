# Конспект теории BPMN 2.0

> Источник: `ИСИТ_Семинар 4_BPMN.pptx` (37 слайдов). Нужна для построения BPMN-модели «как должно быть» по заданию.

## 1. Диаграмма взаимодействия (пулы и потоки сообщений)

- **Поток сообщений (message flow)** — пунктирная стрелка, отображает **межпроцессное взаимодействие**: связь элементов потока со **свернутыми пулами**. Может быть именованным.
- Поток сообщений **не отображает ход выполнения процесса**, а показывает **передачу сообщений или объектов** из одного процесса в другой процесс или внешнюю ссылку.
- Четыре сценария применения потока сообщений:
  1. **Запуск процесса**: поток выходит из внешнего процесса (или внешней ссылки) и входит в **стартовое событие**. Может входить и в промежуточное событие-обработчик — тогда он инициирует лишь возникновение события, а не запуск процесса.
  2. **Входящее сообщение**: из внешнего процесса в одну из **задач** рассматриваемого процесса.
  3. **Исходящее сообщение**: из задачи рассматриваемого процесса во внешний процесс (или внешнюю ссылку).
  4. **Передача по завершении**: поток выходит из **конечного события** во внешний процесс (в качестве источника может быть и промежуточное событие-инициатор).
- **Объекты данных** можно присоединять **ассоциацией к потокам сообщений** — создаются две связи (процесс↔объект данных). Пример из презентации: сдаточная документация поступает в процесс «Организация итогового собрания по проекту» из процесса «Внесение сдаточной документации в папку проекта».
- Схема синхронизации двух процессов (пример): на диаграмме Процесса 1 после его окончания событие инициирует отправку сообщения в Процесс 2; на диаграмме Процесса 2 входящий поток сообщений инициирует событие, запускающее Процесс 2.

### Пример процесса с клиентом (слайд 5 + заметки докладчика)
Процесс инициируется стартовым событием — срабатывает при поступлении **сообщения от Клиента** → Менеджер выполняет задачу **«Получить описание проблемы»** («отправляет» Клиенту уточняющие вопросы, получает более детальное описание) → шлюз «Может ли самостоятельно справиться с проблемой?» → если да: объясняет решение Клиенту, процесс завершается.

Полная версия примера (из заметок докладчика) — **взаимодействие 4 пулов**: Клиент ↔ Менеджер ↔ Агент 1 линии техподдержки ↔ Агент 2 линии ↔ Разработчик ПО:
- если Менеджер не может справиться сам — отправляет **запрос на 1 линию техподдержки**, его процесс **приостанавливается** до получения ответа: это показано **промежуточным событием-обработчиком «Ответ получен» с типом «Сообщение»**;
- Агент 1 линии аналогично: шлюз «Нужна помощь 2 линии?» — да: запрос и приостановка до ответа;
- Агент 2 линии при необходимости обращается к Разработчику ПО; если проблема не решена — включается в план разработки, информация возвращается по цепочке Агент 2 → Агент 1 → Менеджер → Клиент.

Это эталонный образец структуры для нашей диаграммы взаимодействия: несколько пулов, потоки сообщений между ними, приостановка процесса событием-обработчиком.

## 2. Категории элементов BPMN 2.0

Пять основных категорий:
1. **Элементы потока (Flow Objects):** События (Events), Операции (Activities), Логические операторы (Gateways);
2. **Данные (Data)**
3. **Соединяющие элементы (Connecting Objects / Связи)**
4. **Зоны ответственности (Swimlanes / дорожки)**
5. **Артефакты (Artifacts)**

Определения:
- **ОПЕРАЦИЯ** — единица работы, в результате которой **изменяется состояние объекта управления** («Согласовать заявку», «Вынести решение»).
- **ЛОГИЧЕСКИЙ ОПЕРАТОР (шлюз)** — маршрутизирует объект по правилу, не изменяя его («если кредит > 1000 руб., то согласует старший менеджер»).
- **СОБЫТИЕ** используется чтобы: (1) указать **моменты времени** выполнения работы («начать через 1 час после предыдущей»); (2) **ограничить длительность** операций («прервать через 30 минут после начала»); (3) описать **реакцию на внешние изменения** («продолжить после получения сигнала»).

### Классификация бизнес-процессов (схема со слайда 8)
- **Бизнес-процессы управления и развития:** составление каталога товаров, разработка стратегии, составление бюджета.
- **Основные бизнес-процессы:** приём заявок от клиентов, закупка товаров под заказ, доставка заказов, сопровождение клиентов.
- **Вспомогательные (обеспечивающие):** заключение договоров, организация оплаты, организация вознаграждения, размещение рекламы, выбор поставщиков, подбор персонала.

## 3. Операции: задачи и подпроцессы

**Операция (Activity)** подразделяется на:
- **Задачи (Task)** — элементарные действия, не подлежащие декомпозиции;
- **Подпроцессы (Sub-Process)** — составные действия, которые сами могут быть представлены в виде бизнес-процесса.

### Типы задач
| Тип | Суть |
|---|---|
| **Пользовательская (интерактивная)** | Человек — исполнитель, работает при содействии других людей или ПО; типична для технологического процесса |
| **Ручное выполнение** | Только действия человека, без автоматизированных механизмов; **не управляется механизмом выполнения БП** (начало/завершение не отслеживается). Примеры: установка телефонного аппарата у заказчика, проведение совещания |
| **Задача-сценарий (Script)** | Выполняется без участия человека; автоматизированное действие в среде, которая управляет всем процессом (запускает/завершает экземпляры процессов, назначает задачи пользователям) |
| **Сервисная задача (Service)** | Выполняется без участия человека; подключение **сторонних сервисов** вне среды выполнения процесса (веб-сервис, автоматизированное приложение) |
| **Задача бизнес-правило (Business Rule)** | Содержит правила и соответствующие им действия. Само бизнес-правило в BPMN **не моделируется**: оно описывается в произвольном формате (таблица, формулы, код) и обозначается **свернутым пулом**, соединённым **потоками объектов** с задачей типа «Бизнес-правило» |
| **Отправка сообщения (Send)** | Задача выполнена, если сообщение отправлено внешнему участнику **хотя бы один раз** |
| **Получение сообщения (Receive)** | Простая задача: процесс **не продолжается, пока сообщение не получено**; выполнена, если сообщение получено **хотя бы один раз** |

### Маркеры подпроцессов (хорошо/плохо, слайд 9)
- ❌ **Плохо:** свернутый подпроцесс используется как обычное действие в цепочке («Подготовить клиенту» → «Отгрузка товара» без выделения логики).
- ✅ **Хорошо:** большой процесс разделён на **логически очерченные блоки подпроцессов** («Заключение договора» → «Отгрузка товара»).

### Компенсация (слайды 21–23)
- Маркер компенсации может использоваться совместно с другими маркерами.
- **Запуск компенсации** всегда происходит через **событие-компенсацию**, помещаемое на действие, которое может быть отменено.
- Запускаемая задача с маркером компенсации отображается на диаграмме **связью-ассоциацией**.
- Примеры: компенсация с циклом; компенсация с многоэкземплярным событием.

### Условные события (слайды 24–25)
«Иногда нужно начать процесс или продолжить, только если какое-то условие истинно. Всё может быть условием, и условия не зависят от процессов».

### Эскалация (слайды 26–27)
- Событие типа **«Эскалация»** — безусловная передача управления на **уровень родительского бизнес-процесса**, а также обработка таких передач.
- Пример: развернутый подпроцесс «Формирование отчёта»: выгрузка данных → шлюз «Данных достаточно?» → да: сформировать отчёт → отправить заказчику; нет: **завершающее событие-эскалация** → обрабатывается граничным событием → уведомить заказчика о невозможности создать отчёт → конец.
- **Отличия от события «Ошибка»:**
  1. обработчик эскалации **всегда на родительском уровне** относительно события-инициатора;
  2. эскалация может приводить к **положительному** результату, а «Ошибка» подразумевает нештатную ситуацию.

### Отмена (слайд 28)
Событие «Отмена» используется **только в подпроцессах «Транзакция»** для инициирования/обработки отмены транзакций. При наступлении происходит компенсация («откат назад») определённых действий транзакции либо возврат к началу процесса.

### Сигнал vs Сообщение (слайд 29)
- **Сообщение** направлено **конкретному получателю** (адрес, звонок на конкретный номер).
- **Сигнал** не имеет конкретного получателя — это **рассылка неопределённому количеству получателей**: получить и среагировать может любой участник процесса. Сигнал относительно не ориентирован.

## 4. События и их триггеры (слайд 16)

Промежуточные и большинство начальных событий могут иметь **триггеры**, отражающие причину события:

| Триггер | Назначение |
|---|---|
| **Простое** | Нетипизированное событие: начало/окончание процесса |
| **Сообщение (Message)** | Исходит от участника/триггера процесса, предшествует началу, продолжению или окончанию действия |
| **Таймер (Timer)** | Устанавливает цикл времени течения процесса |
| **Ошибка (Error)** | Генерация или обработка заданного типа ошибок |
| **Эскалация (Escalation)** | Перенос рассмотрения вопроса на более высокий уровень иерархии |
| **Отмена (Cancel)** | Указывает на отмену события |
| **Компенсация (Compensation)** | Как подпроцесс может быть скомпенсирован последовательностью отката |
| **Условное (Rule)** | Реакция на изменение бизнес-условий; интеграция бизнес-правил |
| **Связь (Link)** | Подключение окончания одного потока процесса к началу другого потока |
| **Сигнал (Signal)** | Передаётся между процессами, обрабатывается многими получателями |
| **Множественный (Multiple)** | Событие может задействовать несколько путей развития процесса |
| **Параллельный множественный (Parallel Multiple)** | Обработка всего множества параллельных событий |
| **Завершение (Terminate)** | Немедленное прекращение выполнения процесса |

## 5. Граничные события (слайд 20)

- События могут располагаться в потоке управления **между действиями** процесса или **на границе действия** — тогда они считаются **граничными**.
- Граничные события — это промежуточные события на границе действия; обозначают факты, случившиеся при его выполнении.
- **Прерывающие** — прерывают процесс; **непрерывающие** — активируют дополнительный поток, выполняемый одновременно с подпроцессом.
- Пример со слайда: «Проснуться» — простое стартовое событие; граничное **прерывающее** «наступил выходной день» → ветка «Выключить будильник → Уснуть»; граничное **генерирующее** «пришли свежие новости» → «Прочитать новости → Выпить кофе»; простое финишное «Новый день начинается».

## 6. Типичные ошибки BPMN (разбор ошибок, слайды 15–20)

1. **Отправка/получение сообщений:** в примере с КП (коммерческое предложение) взаимодействие с клиентом можно моделировать задачами «Отправить/Получить» **или** промежуточными событиями-обработчиками/инициаторами «Сообщение» — главное не смешивать бессистемно.
2. **Завершающие события:** на диаграмме может быть **несколько конечных событий** — и для потока, и для процесса (не нужно сводить всё в одно).
3. **Шлюзы: одна развилка = одна функция.** Нотация **настоятельно рекомендует не использовать одну развилку и для сведения, и для разведения** потоков управления. Разведение и сведение делают **разными** шлюзами.
4. **Сообщения между процессами, которые могут не успеть:** если задача 2 выполняется быстрее задачи 1, нижний процесс не сможет отправить сообщение — «это сообщение ещё не ждёт верхний процесс». **Решение:** правильно изображать взаимодействие процессов, которые могут выполниться не синхронно (развернуть подпроцесс, перестроить порядок).
5. **Граничные события** нельзя ставить просто «на середину потока» — это события на границе действия.

## 7. Шлюзы (слайды 30–37)

### Эксклюзивный (исключающее ИЛИ, на основе данных)
- Шлюзы **единственного выбора** делятся на: **основанные на данных** (решение по проверке условий переходов) и **основанные на событиях** (решение по происходящему событию — получено сообщение, сработал таймер).
- **Правила оформления эксклюзивного шлюза:**
  1. **перед шлюзом должна стоять задача**, после которой принимается решение;
  2. **ошибка — отсутствие наименования у шлюза** (даже если «и так очевидно»), либо неполное/неточное наименование;
  3. **каждый исходящий поток должен быть подписан** соответствующим решением;
  4. к шлюзу должны присоединяться **взаимоисключающие** варианты решения.

### Пример «Найди ошибку» №1 (слайд 32)
Определение численности сотрудников компании: ветки «до 100 человек», «от 50 до 500», «более 500» — **ошибка: условия пересекаются** (50–100 подходят под две ветки) — нарушено правило взаимоисключающих вариантов.

### Пример «Найди ошибку» №2 (слайд 33)
Подготовка отчёта и пакета документов: параллельный шлюз (+) разводит две ветки (составить отчёт / собрать пакет документов), а сведение сделано **эксклюзивным (X)** шлюзом — **ошибка: параллельные ветки нельзя сводить исключающим ИЛИ**. Правильно: сведение тоже **параллельным** шлюзом.

### Событийный эксклюзивный шлюз (слайд 34)
«Логический оператор исключающего ИЛИ, управляемый событиями» — выбирает альтернативный маршрут процесса. Исходящие потоки должны быть связаны **только с событиями или задачами-обработчиками сообщений**. Поток идёт по ветви, **событие по которой наступит раньше других**; остальные события игнорируются.

### Параллельный событийный шлюз с созданием нового экземпляра (слайд 35)
Пример — ежемесячное выставление счетов за консультации. Счёт выставляется, когда **выполнены все условия**:
1. количество часов консультаций **больше нуля** → событие-обработчик типа **«Условие»**;
2. получен согласованный **лист учёта рабочего времени** → тип **«Сообщение»**;
3. наступило **1 число месяца** (счета выставляются помесячно) → тип **«Таймер»**.

Событийный оператор **И** отслеживает наступление всех трёх событий и запускает новый экземпляр бизнес-процесса выставления счетов.

### Сложный шлюз (Complex Gateway, слайды 36–37)
Используется, когда **все остальные шлюзы не могут отобразить логику переходов**. **Крайне не рекомендуется**: к нему потребуются пояснения автора схемы.

## 8. Шпаргалка: что проверить в своей диаграмме

- [ ] У каждого эксклюзивного шлюза есть **название** и **подписанные взаимоисключающие** выходы; перед шлюзом стоит задача.
- [ ] Разведение и сведение потоков — **разные** шлюзы; параллельные ветки сводятся параллельным шлюзом.
- [ ] **Потоки сообщений** (пунктир) идут только между пулами; старт по сообщению — через стартовое событие.
- [ ] Задачи выбраны правильных типов (человек = пользовательская; автоматика = сервисная/сценарий; расчёт по правилам = бизнес-правило).
- [ ] Таймеры/условия/сообщения использованы там, где процесс ждёт внешнего события.
- [ ] Несколько конечных событий — норм; каждое осмысленно.
